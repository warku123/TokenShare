Idle official-plan quota, sold by the call. KIMI / MOONSHOT FIRST

In plain words: paying for a Kimi plan you never fully burn through? Sell the leftover quota by the call — buyers pay per request, you keep the plan.

Sellers rent out the spare quota of their official LLM subscription plans — a relay holds their own platform key and forwards only to the provider's official endpoint. Buyers lock a few cents of USDC on-chain and pay per request. An immutable escrow holds the funds, settlement is priced on relay-reported usage in three tiers, and every call comes back with an EIP-712 receipt anyone can verify. Seller keys stay off-chain; the escrow holds only USDC. Custody modes, receipt limits & refund rules → policy.

02MECHANISM

One call, five transitions. Funds move only through the escrow; the relay never touches money and the contract never touches keys.

1

DEPOSIT

deposit()

Buyer funds an escrow balance in USDC. One deposit backs many calls.

2

LOCK

lock(seller, maxAmount, ttl)

Reserves up to maxAmount for one seller and returns a fresh paymentId — default ttl 600s.

3

CALL

isValid(paymentId)

Relay checks the lock on-chain before forwarding. An invalid proof gets a 402 — zero cost, never upstreamed.

4

SETTLE

settle(paymentId, actual)

Usage priced in three tiers; the seller settles actual ≤ max and the difference returns to the buyer.

or
5

REFUND

refund(paymentId)

No settle before the deadline → anyone releases the lock. The un-captured remainder returns to the buyer.

same flow, raw — cast + relay log
$ cast send $USDC "approve(address,uint256)" $ESCROW 500000
$ cast send $ESCROW "deposit(uint256)" 500000 --rpc $MONAD_RPC
$ cast send $ESCROW "lock(address,uint256,uint256)" $SELLER 50000 600
# relay: Escrow.isValid(paymentId, seller=self, minAmount=est) — false → 402, no forward
# relay: forward to api.moonshot.cn with seller's own official-plan key · usage from response
# pricing: 12000×cached + 26400×in + 2140×out = 45552 units = 0.045552 USDC
$ cast send $ESCROW "settle(uint256,uint256)" $PID 45552 # seller only
# buyer diff 4448 → balances[buyer] · X-Receipt: EIP-712 {paymentId, usage, actual, seller, upstreamHost, model}

03ESCROW STATE MACHINE

Four states, five transitions, no admin path. Hover a state to trace its edges.

  1. deposit()→ Deposited
  2. lock(seller, maxAmount, ttl=600)→ Locked · emits paymentId
  3. settle(paymentId, actual)→ Settled · seller only · diff → buyer balance
  4. refund(paymentId)→ Refunded · after deadline, anyone can trigger
  5. withdraw()→ idle · unencumbered balance out

04DESIGN CONSTRAINTS

The things the protocol refuses to do are the features.

KEYS OFF-CHAIN

Contracts never see a key, a prompt, or a completion. Single mode: keys live in the seller's own relay. Shared mode (live): sealed inside a platform TEE relay (see policy). The escrow holds USDC — nothing else.

VERIFY, THEN FORWARD

Every request is gated by an on-chain isValid(paymentId) check. Unpaid calls get a 402 and cost the seller nothing. Payment proof comes first, inference second.

OFFICIAL ENDPOINTS ONLY

The relay boots only against the provider's official host allowlist (api.moonshot.cn/.ai, api.openai.com) and rejects models whose prefix doesn't match the host — no lookalike endpoints, no poisoned models. Every receipt records upstreamHost + model.

ONE BYTECODE, NO KEYS

No proxies, no admin keys, no upgrade path. Chain-agnostic by config, delivered on MONAD TESTNET · 10143 with immutable contracts — what you read is what you get.
